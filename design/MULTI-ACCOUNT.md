# 多账号与多服务商：首版接入边界

2026-11-17。延续 [邮件核心设计](MAIL-CORE.md)，不增加服务端或通用 provider 框架。

## 继续复用什么

现有 Account、每账号同步进程、数据库和任务队列继续使用。统一收件箱只是跨账号查询；跨账号批量操作拆成现有的账号内任务，逐项返回结果，不承诺一起成功或一起回滚。

邮件、会话、草稿和操作引用都带 `accountId`。两个邮箱收到相同 Message-ID，仍是两个独立对象。CLI 继续通过桌面共用核心处理邮件，不持有邮箱凭据或另起同步实例。

## 服务商差异放在哪里

| 差异 | 首版处理 |
| --- | --- |
| 登录 | 保留普通 IMAP / SMTP 凭据；Google Desktop OAuth 是单独的接入流程。不能仅因识别为 Gmail 就切换 IMAP 认证方式。 |
| 发信 | 普通账号使用 SMTP；已配置 Google 授权的 Gmail 显式使用 HTTPS。失败不自动换通道再次发信。 |
| 归档与恢复 | 依据同步得到的文件夹／标签能力：普通 IMAP 移动文件夹；Gmail 在 All Mail 上修改 Inbox 标签，需要时移动 Spam / Trash。 |
| 服务器目录 | 使用已有特殊用途映射和用户文件夹设置；缺少目标目录时明确显示操作不可用，不猜英文目录名。 |
| 连接状态 | 每账号同步、重连和报错；一个账号认证失败不阻塞其他账号。 |
| Agent 范围 | 沿用账号及排除目录／标签授权；查询旧操作和撤销也使用当前授权。 |

这里是三个具体差异点：登录、发信、邮件整理。暂不建立 provider 注册表、插件接口、第二套任务队列或能力数据库。

## 界面行为

- 账号设置沿用“添加账号”、账号名称与自定义颜色；列表通过既有账号筛选切换统一视图／单账号。
- 单账号视图新建邮件使用该账号。统一视图当前使用第一个账号；正式多账号日用前，应明确默认发件账号并验证发件人选择与回复归属，不能把排序当成用户偏好。
- 草稿建立后绑定账号；回复使用原邮件账号。不要通过改一个 `accountId` 把已有草稿、附件和发送记录搬到另一个账号。
- 批量整理显示每项结果。只有部分成功时，撤销成功项，不把失败项显示为已处理。

## 验证状态与推进顺序

| 范围 | 当前证据 |
| --- | --- |
| 单个真实 Gmail | 已验证授权、IMAP 收信、CLI → GUI 草稿交接、用户批准的一次 HTTPS 自发自收和重启；见 [真实接入记录](../research/gmail-integration-validation-2026-11-17/README.md)。 |
| Gmail + 普通 IMAP 同时运行 | 已用本机协议服务器、实际桌面／CLI／原生引擎验证统一收件箱、账号筛选、整理及撤销、草稿隔离、权限与单账号认证失败；见 [混合账号验证](../research/gmail-mailbox-validation-2026-11-17/README.md)。 |
| 两个真实服务商同时使用 | 尚未验证。协议 fixture 通过不等于 Outlook、iCloud 或其他服务商已经接通。 |

下一轮先选一个非 Gmail 的专用测试账号，用已有 IMAP / SMTP 接入验证真实双账号收发、回复身份、默认发件账号与重启恢复。若该服务商必须使用 OAuth，再为它增加独立登录适配，并使用 Paper Reed 自己的应用注册信息。SMTP 在当前公司网络的可用性也需实际检查；Gmail 的 HTTPS 成功不能替它作证。

后续再扩展其他服务商。账号数量、登录政策和真实协议差异推动实现，不先写一套假定所有邮箱都适用的抽象层。
