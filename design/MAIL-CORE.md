# 首版邮件核心设计

2026-11-15 · 待评审的行为方案，不是已确定的技术选型。界面按用户确认暂作第一版基线，接下来用本文约束技术实验；不新增产品实现。

**目标：一份本机邮件状态，桌面界面与 CLI 使用同一套查询和修改能力。** 首个闭环是 Agent 读取邮件并创建回复草稿，用户在界面继续编辑、发送，双方看到一致的结果。

## 1. 首版做到哪里

| 纳入核心 | 边界 |
| --- | --- |
| 多账号与统一收件箱 | 每个账号独立同步；统一收件箱只是查询视图 |
| 阅读与搜索 | 查询已同步的邮件；明确缓存范围，正文或附件未下载时说明缺失，不伪装成空内容 |
| 写信、回复、附件、发送 | 同一份草稿供界面与 CLI 继续编辑；发送前校验发件身份、收件人和附件是否就绪 |
| 基础整理 | 已读、归档、移入垃圾邮件／废纸篓和恢复；根据账号能力开放操作 |
| 本机整理 | 置顶、稍后、自定义标签；分类先用显式规则，不要求 AI |
| 外部 Agent | 查询、整理、草拟、发送分开授权；CLI 可查询操作结果 |

暂不做云端业务后台、跨设备本机状态同步、移动端、多人协作、插件平台、内置 AI、定时发送或永久删除。账号支持清单由真实连接实验决定，不能因为界面有服务商按钮就声称已支持。

**分两步交付，避免把第一项实验变成完整客户端：**

1. 先验证两个测试账号、缓存查询、回复草稿、发送与归档，以及 UI / CLI 一致性。
2. 再接入置顶、稍后、标签和简单分类规则，并验证完整界面流程。规则只支持原型已有的“发件人／主题包含 → 加本机标签或设置分类”；顺序执行，多个标签可累加，分类采用最后一个匹配结果。关闭规则不撤销历史结果，处理已有邮件需显式选择。

## 2. 只有一个邮件核心

```text
桌面界面 ─┐
          ├─ 邮件核心（查询、修改、权限、操作结果）─ 同步／收发引擎 ─ 邮箱服务商
CLI ──────┘                    │
                         本地存储与变更通知
```

这是职责边界，不是四个新进程。优先利用候选底座已有的存储、任务和通知机制，不叠加第二套数据库或队列。CLI 不直接改数据库，也不自己登录邮箱；界面不得绕过核心另做发送逻辑。

保留三个代码边界就够：界面、邮件核心、CLI 适配。服务商差异先藏在收发引擎及少量适配代码里，不先做通用插件接口、CommandBus、事件溯源或依赖注入平台。是否使用 IPC、socket 或已有本机接口，等技术验证后选。

第一版核心随桌面应用运行。关闭窗口可继续后台工作；明确退出应用后 CLI 返回“应用未运行”，不另启一个同步实例。尚不提供独立 headless 服务。

同步按账号独立推进：引擎保存进度并增量更新缓存，一个账号需要重新登录不阻塞其他账号。先取得列表所需信息，正文与附件按需加载；搜索说明已覆盖范围。断网、重启和唤醒后由引擎恢复并核对远端变更，本地查询始终读缓存。首版不另做实时全邮箱搜索或自己的同步协议层。

## 3. 最小数据模型

下面是逻辑对象及必要信息，不是要求新建同名表；优先映射候选引擎已有模型。术语见 [GLOSSARY.md](../GLOSSARY.md)。

| 对象 | 必要信息与约束 |
| --- | --- |
| Account | 稳定账号标识、显示名、账号色、发件身份、连接状态、可用操作；凭据通过系统凭据存储引用，不进入 CLI 输出 |
| Message | 账号、稳定邮件标识、远端定位信息、会话标识、信封信息、正文／附件缓存状态、已读及服务端归属 |
| Thread | 账号内的会话标识与成员邮件；主题、摘要和未读数等可以从邮件派生，不复制第二套正文 |
| Draft | 稳定草稿标识、账号与发件身份、To/Cc/Bcc、主题、正文、附件、回复目标、修订号、编辑／提交状态 |
| 本机会话状态 | `(accountId, threadId)` 对应的置顶、稍后到期时间、稍后开始时的新来信基准、本机标签和分类 |
| Label / Rule | 标签的标识、名称和颜色；规则的匹配条件、动作、启用状态与顺序 |
| Operation | 操作标识、请求去重标识、账号、明确的目标及动作参数、执行状态、错误、必要的结果引用 |

约束：

- 所有外部可引用的邮件／会话标识都附带 `accountId`，不能靠主题、邮箱地址或内容摘要定位修改对象。
- 一封邮件可能属于多个服务端位置；不采用原型的单一 `folder` 字段作为真实存储模型。服务端归属与本机标签分开保存。
- 相同内容进入两个账号时保留两份独立对象，不跨账号去重。账号内部移动或重新同步应尽量保留本地对象标识；远端定位变化由引擎处理，无法确认映射时先重同步，不猜测修改目标。
- 会话分组优先使用引擎已经验证的关系，不仅凭相同主题合并。置顶、标签与稍后需要稳定会话映射，这是底座实验的验收项。
- 草稿独立于原邮件；“回复草稿”不是在收件邮件上增加一个可编辑正文字段。保留准确回复目标及必要的回复头信息。
- 附件作为邮件／草稿的一部分管理，初期不另做素材库。添加本机文件后保存可持久读取的副本；源文件被移动也不能悄悄丢失附件。

## 4. 谁保存什么，修改到哪里

| 状态／操作 | 首版约定 |
| --- | --- |
| 已收到的内容、已读、服务端归属 | 以邮箱服务端为准，本机缓存；本机待执行修改单独标识，不能被一次旧同步覆盖成“已成功” |
| 归档 | 通过引擎执行“离开收件箱”的账号适配操作，不删除邮件、不清除无关标签；账号无法支持时明确禁用 |
| 垃圾邮件、废纸篓与恢复 | 根据账号能力执行；Paper Reed 发起的移动保留恢复所需信息。外部已移动邮件无法得知原位置时只承诺“移回收件箱” |
| 置顶 | 仅本机；不占用服务商星标，也不把已归档邮件重新放入收件箱 |
| 稍后 | 仅从本机收件箱隐藏，保留远端归属。到期或出现新的外部来信时解除；不能把首次补齐历史缓存当成新回复。垃圾邮件／废纸篓不因到期自动恢复 |
| 自定义标签 | 本机、可跨账号使用；名称与颜色共用，和服务商标签完全独立，不向远端创建同名标签 |
| 往来／通知／订阅 | 本机分类；首版允许手动纠正及简单规则。无法确定的来信保留普通分类，不阻塞收信 |
| 草稿 | 首个闭环以本机持久草稿为准；明确显示“已保存到本机”。远端草稿同步是下一项实验，不静默导入、覆盖或删除服务商草稿 |

草稿同步是否进入可日用的首版，需要在底座验证时明确：若引擎已有可靠路径则复用，否则如实保留“本机草稿”限制；**不能将这项未验证能力写成已支持跨设备续写**。服务端已有草稿的编辑／发送不属于第一个实验的验收范围。

稍后时间保存为绝对时刻，按系统时区显示。应用退出期间不运行额外定时服务，下次启动后立即处理已到期项目；睡眠唤醒也重新检查。

归档／移动等“会话操作”作用于受理时明确记录的成员邮件。之后到达的新回复不被旧任务顺带归档。稍后、置顶与本机标签则附着于会话。批量操作逐目标返回结果，允许部分成功，不假装跨账号事务。

## 5. UI 与 CLI 的共同操作面

这里只定义语义，不锁定命令名、类名或传输协议。

| 能力 | 输入与结果 |
| --- | --- |
| 列账号、查列表、搜索 | 账号范围、筛选、游标、页大小；返回对象引用、缓存／同步状态和下一页游标 |
| 读会话／正文／附件 | 账号与对象引用；返回内容或明确的未缓存／不可用状态 |
| 新建／修改草稿 | 发件身份、回复目标或新邮件字段；返回 `draftId` 与 `revision` |
| 整理会话 | 明确目标、动作、参数、请求标识；返回 `operationId` 和当前状态 |
| 提交发送 | `draftId`、`expectedRevision`、请求标识；返回 `operationId`，后续查询发送结果 |
| 查询操作 | `operationId`；返回阶段、错误和结果引用，不靠解析界面提示判断成功 |

- 界面和 CLI 修改草稿都携带读到的修订号。若另一方已经保存，拒绝旧修订覆盖并让调用者重新读取；首版不做自动合并编辑。
- 草稿成功保存后即成为两端可读的同一对象。界面通过变更通知刷新，断线后重新查询；不要求 CLI 实现常驻订阅。
- 进入发送时锁定该修订并冻结收件人、正文和附件。明确失败可回到可编辑草稿；结果待确认时保留冻结版本，防止误当作另一封信重发。
- 列表交接必须明确账号、已选对象或受限查询范围。执行修改前固定目标集合并显示数量；不能把“当前页面”静默扩大为所有历史邮件。
- CLI 输出稳定 JSON 和可读错误；等待超时只表示停止等待，仍返回可查询的操作标识。

## 6. 操作结果与离线恢复

仅远端操作需要持久任务；本机草稿、标签、置顶可以提交本地事务后直接完成。若底座已有任务记录，映射它，不再造调度系统。

远端任务采用少量状态：`queued`（待执行）、`running`、`succeeded`、`failed`、`unknown`（结果待确认）、`cancelled`（未执行即取消）。是否已本地呈现独立记录，不把“界面消失”当作服务器完成。

- 离线可以看已缓存内容、编辑本机草稿、做本机整理；普通远端整理可以排队，界面说明待同步。首个闭环离线时不接受新的发送提交，保留草稿并提示联网后再发。
- 重启后恢复待执行整理任务；根据最新同步状态核对结果，再决定是否重试。先验证“设置为已读”等明确目标状态，避免用“切换已读”重放任务。
- 发送请求标识在发件前持久保存。相同标识、相同参数返回同一个结果；相同标识、不同参数拒绝。未解决的同一草稿发送也不能靠换请求标识绕过。
- 发送过程中断连、崩溃或丢失响应，若无法确定是否已接受，标为 `unknown`，**不自动再次发送**。先经引擎核对发送记录／已发送邮件；仍不能确定时交给用户处理，不能只凭主题相同判定成功。
- “发送成功”仅指发件服务器已接受。已发送文件夹副本的同步可以稍后完成，失败时提示保存副本问题，不能再次投递来修复副本。
- 服务器接受后，该修订退出可编辑草稿列表，保留发送操作与内容引用供核对；明确失败保留草稿，结果待确认时显示发送状态，不当作普通未发送草稿。回复发送本身不隐含归档原会话。
- 撤销本机整理可以直接恢复；远端操作未执行时可以取消，执行后需提交反向操作并反馈其结果。首个闭环不承诺已提交发送可撤回。

不追求跨服务商的“恰好一次”承诺。首版重点是不会因为超时、重复点击或 Agent 重试而悄悄重复投递。

## 7. Agent 权限只保留必要层次

设置中沿用已设计的三组能力：**阅读与搜索、整理与草拟、发送邮件**，外加明确账号范围。发送独立开启，默认不授权；第一次实验由用户在界面确认发送，受控自动发送随后验证。已授权范围内不再逐封弹窗。

权限在核心入口检查，远端任务执行前再次检查；撤销授权后取消尚未执行的对应 Agent 任务，已经提交到服务器的请求不能承诺撤回。读取操作结果、附件和搜索也必须校验账号范围。批量请求遇到未授权目标明确拒绝该项；交接界面可先展示授权范围内的子集，但不能静默少处理几封。

第一版可以共用一套本机自动化授权，不引入角色体系、团队权限或每个 Agent 的账户系统。邮箱凭据不交给 Agent。收件正文属于不可信内容，不能通过正文里的指令扩大工具权限；邮件 HTML 隔离渲染，不获得桌面应用权限。

## 8. 用这些场景决定技术路线

| 实验 | 必须看到的证据 |
| --- | --- |
| 两个不同账号收到相同内容 | 独立引用；归档或回复一个账号不会影响另一个 |
| CLI 创建回复草稿 → UI 修改 | 相同草稿标识；CLI 重读能看到最新内容；旧修订不能覆盖；Cc/Bcc、换行、附件、回复关系不丢 |
| UI 确认发送 → CLI 查询 | 返回同一操作；正确发件身份；服务器接受与已发送副本同步分别可知 |
| 重复请求、断网、重启 | 整理可恢复；相同发送请求不重复提交；发送不确定时不自动重投 |
| 未授权账号或发送能力关闭 | 操作无副作用；搜索、附件、结果查询也不能越权 |
| 本机稍后／标签与外部变更 | 标签不修改远端；新来信解除稍后，历史补齐不解除；到期不恢复垃圾邮件 |

选型只比较能否通过这些实验、实际改动量、维护成本与安装分发限制。不要先写一个只覆盖模拟对象的通用引擎，再寻找可用的邮箱接入。

**下一项具体工作：** 基于已有 [源码研究](../research/README.md)，先验证候选同步引擎能否暴露稳定对象标识、草稿修订和可靠操作结果。优先跑通一个账号，再加入第二种账号验证差异；据结果决定复用 Mailspring 还是另建核心。框架、数据库、协议、OAuth 接入与草稿远端同步都在实验结论中再定。
