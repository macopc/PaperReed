# 实施质量审查

审查基线：`bc5d15bd62e13f041794da27a1bd60e44a32312e`，包含 0001–0020 全部实验补丁。使用 Good Offence 的判断方法：沿真实调用链验证保护措施的前提，优先减少重复职责、错误转换和隐藏状态；不以代码行数、检查次数或抽象数量直接判定过度设计。

结论：当前没有需要推倒重来的架构问题，但已经出现应先收敛再继续扩功能的实现债。最优先的是一处已复现的数据丢失竞态。其余集中在附件错误与文件的生命周期、读路径依赖全局写队列、短期去重状态没有自然结束，以及诊断信息被吞掉。实验闭环通过不等于这些路径已经可靠。

此次只审查，未修改产品代码。先前附件／CLI 改动已提交推送；本报告和审查证据是后续新增文件。

## 1. P1：普通关闭路径把“保存完成”误当成“没有新编辑”

位置：`app/src/flux/stores/draft-store.ts:126–130, 193–198`；相关实现见 [关闭保护](../patches/0005-unsaved-draft-close.patch) 和 [附件等待](../patches/0020-attachments-cli-compose.patch)。

`_saveSessionBeforeClose()` 等待一次 `commit()` 后直接返回 true；所有保存完成后，`_onBeforeUnload()` 清空会话并关闭。`DraftChangeSet` 本来会把保存期间的新编辑保留为 dirty，但关闭方没有读取这个事实。

**已在真实窗口复现**：编辑正文 → 请求关闭 → 暂缓原生保存回执的交付 → 在仍可编辑的窗口继续输入 → 释放回执。窗口关闭，重新读取草稿时第二段输入消失。数据库保存和实际关闭都使用产品路径，只在保存回执边界控制顺序；SMTP 提交为 0。

这不是需要增加锁来覆盖的罕见进程故障，而是已有异步保存期间仍允许编辑的正常状态组合。冲突另存路径已检查保存期间是否又编辑，普通关闭路径反而没有。

**建议**：把关闭完成条件明确为“当前会话已无脏编辑和待加入附件”；有新编辑则保持窗口和提示。复用工作台 `move()` 已有的完成后检查，不新增重试循环、第二套锁或统一工作流框架。最终清空会话／关闭也应遵守同一完成条件。

## 2. P2：附件错误被吞掉、存入旁路状态，又由第一个等待者清除

位置：`app/src/flux/stores/attachment-store.ts:483–503`；[0020 补丁](../patches/0020-attachments-cli-compose.patch)。

`_onAddAttachment()` 捕获失败后让队列 Promise 成功，将错误放进 `_attachmentErrorsByDraft`；`hasPendingDraftAttachments()` 再把这个错误解释为 pending；`waitForDraftAttachments()` 删除错误后抛出。一个失败跨了三个不同语义，保存、关闭、发送和另存副本都能消费它。

**已复现**：对真实不存在的文件执行添加，两个并发等待者分别得到 `rejected` 和 `fulfilled`，之后 pending 变为 false。相同操作的结果取决于谁先读取。这也意味着“待处理”可能实际上已经失败，而后续新尝试不会自然替换旧错误。

**建议**：保留“不同附件失败不阻塞后续添加”的队列行为，但让同一批添加拥有稳定的完成结果；所有等待者看到一致结果。pending 只表示进行中，重试／放弃是明确的状态更新，不由读取错误隐式推进状态。将错误展示留在 UI 边界，避免 Promise 成功后又从隐藏字段还原失败。

## 3. P2：收件箱读取被全局整理队列阻塞，局部状态查询又重复读取同一会话

位置：`app/src/services/mail-core/inbox.ts:64–65`、`local-triage.ts:51–53, 94–109, 161–186, 302–351, 624–681`；[0018](../patches/0018-local-triage.patch)、[0019](../patches/0019-local-rules-classification.patch)。

`queryInbox()` 每次都等待 `reconcileLocalSnoozes()`，后者与规则执行、批量整理、标签修改共用单个 `serial()` 队列。后台规则会在队列内逐封异步读取消息／会话，队列范围跨账号。用户的读取因此依赖不相关写工作的完成。

**已验证等待关系**：只暂缓一次置顶操作的正常会话读取，此时独立的标签读取已完成，收件箱查询仍在等写队列；释放该读取后才继续。这是依赖关系实验，不把注入的延迟当作生产性能测量。

此外，8 个会话的 `localStates()` 实际调用了 16 次 `Thread` 单项查询，外加每项两次本机状态／标签查询。工作台还逐项查摘要。验证和读取分散在多个 helper 中，使列表刷新工作量按行数叠加。

**建议**：先让读路径不启动并等待全局整理扫描，借助已有后台整理及变更通知更新视图；到期的可见性可直接按查询时刻判断。将状态／标签／可见性所需数据批量读取，在一致快照上检查授权。把写操作串行化范围收回短事务，保留必须的读改写一致性。不要改成“每个对象再加一把锁”，也不要直接删除权限检查。

`sql` 使用同步 better-sqlite3，却包成 async，容易误以为这是后台 I/O。它仍在 renderer 执行，配置的 10 秒 busy timeout 也不会被 async 消除；这应在收敛读写边界时明确，而不是再叠一层应用重试。

## 4. P2：临时 pending 去重依赖调用方轮询才能回收

位置：`app/src/services/mail-core/inbox.ts:109–111, 148, 199–202, 275–282, 294–324`；[0017 补丁](../patches/0017-inbox-operations-search.patch)。

成功提交的 Promise 留在模块级 `pending` Map；正常成功路径不移除。回收发生在之后的 `receipt()`，即调用方再查询状态或重复请求时。短暂的入队去重因此被实现成生命周期不明确的内存记录。

**已复现**：CLI 发起标为未读，直接观察原生 Task 已 complete；Map 仍保留 1 条。调用 `change-get` 后才变为 0。若 CLI 调用方退出或中断，不再轮询，完成任务会留在 Map，和有界 Task 历史脱节。

**建议**：pending 只覆盖“任务尚未形成可查询原生记录”的窗口；由提交完成／失败自己释放，之后依赖已有 Task 记录。若需要等待，等待已有受理回执，不添加 TTL 缓存、后台清理线程或第二套持久任务表。不能在 `queueTask()` 返回时就无条件清除，否则原生记录尚未落地的去重窗口又会打开。

## 5. P2：为保护未保存版本而永久保留附件，把正确保护扩大成无界存储

位置：`app/src/flux/stores/attachment-store.ts:53–57, 598–608`；`app/src/services/mail-core/index.ts:84–101, 133–154, 210–216`；[0020 补丁](../patches/0020-attachments-cli-compose.patch)。

移除／丢弃草稿在 Paper Reed 模式下不删除附件；添加和另存副本先复制文件，后续保存失败没有对应的文件所有权收尾。发送时又产生独立快照，发送成功清理的是快照，而不是原草稿文件。因此即使只走普通的“附加 → 发送”流程，也会保留不再由草稿引用的原文件。

这是上一轮已记录的限制，不是假装新发现。独立副本和不立即删除有实际价值；问题是没有明确何时不再需要保护这些字节。每封邮件 25MB 的限制不限制长期累积。

**建议**：先定义三种现有所有者——已保存草稿、打开的编辑会话、未解决的发送操作——对应的生命周期。明确未受理的失败可释放本次新建文件；结果不确定时继续保留。应用启动时、打开编辑会话之前做一次保守的未引用临时附件清理，比新增常驻 GC 服务或全局引用计数框架更合适。清理必须限定本应用生成的临时附件，保留当前草稿和未解决操作所需文件。

## 6. P3：宽泛吞错和重复保存断言，让成功契约不够清楚

位置：`app/internal_packages/paper-reed/lib/workspace.tsx:271–291`，`app/src/services/mail-core/index.ts:59–62`，`app/src/flux/stores/draft-editing-session.ts:537–546`。

- 发送结果刷新把所有异常静默吞掉，注释却只解释 fixture 初始化时表未建立。真正的查询错误或坏 payload 同样不留下诊断，UI 保留旧结果。应只识别初始化未就绪，其他错误保留诊断并让用户看到结果暂不可读；不需要新增自动重试层。
- `saveDraft()` 已执行 `assertSaved()`；目前 `acceptSaveReceipt()` 的调用方都来自这个服务，却再次断言，并对缺少 `savedDraftRevision` 静默跳过。建议让 `saveDraft` 返回明确的成功回执（ID、修订），在这一个边界保证完整性，内部调用者直接使用。原生 CAS 和外部输入校验仍保留。

这些是小范围收敛项，优先级低于前面的数据丢失和生命周期问题。不要为了统一错误建立一个跨全项目的异常层。

## 工程交付债与审查边界

仓库仍以补丁为产品实现载体，实际源码 checkout 和本轮使用的补丁导出／重放脚本在 ignored 目录。现有 GitHub CI 运行 `scripts/check.py`：验证原型、JS 语法、JSON、链接，不应用补丁，也不编译产品 TypeScript。人工跑过重放／类型检查是有效证据，但后来提交无法自动继承这项保证。

探索阶段可以继续使用补丁，不必为了审查立即搬迁整个上游仓库。最小改进是提交一个固定基线的准备／顺序重放／类型检查入口，并接入适当的 CI；不要继续复制一份临时脚本来支持每一轮新补丁。当前报告不等同于对整个上游代码的全面审计。

没有把以下已知范围当作本次新发现：真实服务商和 OAuth 未验收、正式迁移／安装包未完成、撤销 Agent 权限后的原生待执行任务尚未完整处理。它们仍是日用前需要收口的事项。

## 应保留的保护与下一步

应保留：原生事务中的草稿修订检查、发送请求去重和 unknown 状态；GUI／CLI 汇合到同一保存边界；原始文件、草稿、恢复副本与发送快照之间的独立附件；外部输入的格式／范围校验；跨异步读取后重新检查当前授权；队列尾部捕获失败以保证后续工作可继续，同时向原调用者保留原 rejection。

这些机制保护真实的多入口和异步状态变化。移除它们不会使架构更简单，只会把问题推给调用方。未发现需要再引入通用队列、锁管理器、事件溯源、插件平台或新的服务进程的证据。

建议先修普通关闭竞态，再统一附件完成／失败语义和 pending 生命周期，随后收敛列表读路径与附件清理，最后补可复现的自动检查入口。每次修复使用最小的行为回归，不再增加“等一会儿也许就好了”的延时兜底。

## 证据

[evidence.json](evidence.json) 保存真实运行结果，包括关闭时丢失的后续输入、两个附件等待者的不同结果、局部状态读取次数、收件箱等待关系和 pending 回收时机。两次隔离运行 SMTP 提交均为 0。

测试仅使用独立本机账号与 fixture 文件。关闭竞态暂停的是实际 native 保存回执；整理等待实验暂停一次普通会话读取；pending 实验只观测 Map 更新和真实 Task 完成。未直接修改产品数据库或用假发送器伪造结果。复现探针保存在当前工作区的 `research/.local/quality-review/`，不作为新的产品实现提交。
