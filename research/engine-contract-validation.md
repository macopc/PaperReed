# 邮件核心契约：真实引擎验证

2026-11-15 · 接续 [本机验证](native-validation.md)。**四个实验复现了草稿覆盖、重复发送和中断后结果不明的问题；不是四项产品验收通过。** 这将此前源码分析推进为运行证据，也确认现有 MCP 外面包一层 CLI 不足以满足首版邮件核心设计。

## 实验范围

使用同一固定路径下载的预编译 mailsync，SHA-256 为 `cbc1b2ac4cd21f98df7c14759d2145bc17888a83ecab5ff0c3005ddac4776448`。完整上游 checkout / 子模块仍为 `535f13dd` / `8681eae1`。C++ 源码构建仍受 Xcode 环境阻塞，没有把预编译产物视作本轮自编译产物。

引擎通过 stdin 接收真实任务，并与本机 fake:dovecot IMAP / SMTP 服务通信；观察数据库时只读 SQLite，不修改数据库来制造结果。使用 `identity=null` 和仅本机网络沙箱，无真实邮箱账号、外部 SMTP 或上游业务服务。

这轮验证引擎层语义，未经过完整 GUI / MCP 调用链。重复任务输入对应 [此前 MCP 处理器实验](tech-selection-validation.md) 已观察到的重复入队；不能泛化成所有用户操作都会重复发送。

## 四个结果

| 实验 | 操作与观察 | 对 Paper Reed 的影响 |
| --- | --- | --- |
| 旧草稿覆盖 | 创建草稿修订 1；“用户”基于它保存新正文，库版本变为 3；“Agent”再提交基于版本 1 的旧副本，库版本变为 5，新正文被覆盖，任务无错误 | 现有版本号只随保存增长，不能代替原子冲突检查 |
| 同一草稿重复发送 | 保存一份草稿，将同一内容提交为两个不同 task id；本机 SMTP 实际接收 **2 次**，Message-ID 相同 | 引擎不会合并同一草稿的不同发送任务；必须在提交边界持久去重 |
| 正文提交前崩溃 | 在 SMTP 即将返回 `354`、引擎尚未提交正文时暂停；确认任务已持久写入 `_performRemoteRan=true`，对引擎发送 SIGKILL，再用同一库启动新进程 | SMTP 接收 **0 次**，恢复后任务却为 `complete`，无 error；不能按此状态宣布发送成功 |
| 正文接收后、确认前崩溃 | 本机 SMTP 已保存一份非空正文，但最终 `250` 尚未返回；同样 SIGKILL 并重启 | SMTP 接收仍为 **1 次**，未自动重发；恢复后同样是 `complete`、无 error，无法与上一种状态区分 |

这两个崩溃案例没有观察到自动重复投递；问题是**恢复后的任务状态抹平了“根本未提交”与“服务端已接收”的差别**。若界面或 Agent 把该状态映射为“已发送”，就会误报。正文被本机 SMTP 接收也不等于送达真实收件人。

输出见 [机器可读结果](engine-contract-results.json)。其中 `observation_reproduced: true` 表示复现成功，`paper_reed_contract_met: false` 表示没有满足产品约定。

## 故障注入如何保证有效

仅修改本次 Python 测试服务的响应函数：在指定 SMTP 响应发出前阻塞，检查数据库中已持久化的任务状态，然后实际杀死引擎进程。没有编辑引擎源码、伪造任务状态或把正常退出当作崩溃。重启时重新运行迁移，保留同一数据库和协议服务。

测试服务原始 DATA 循环可能把连接 EOF 当成一封空邮件。故障注入器会显式终止被中断的测试连接，避免这个 fixture 行为污染计数；同时检查被接收的正文非空。初次调试时受到该行为影响的计数未纳入结果。最终四个实验完整执行成功。

每个场景使用独立临时目录；崩溃场景额外保存杀进程前的 task 快照与日志，重启日志和结果保留在 `research/.local/contracts-*/`。这些目录不入库。

## 最小修正范围

继续选择复用路线，但需要产品分支中的小范围引擎与入口改动，不能仅改提示文案：

1. **原子保存草稿。** 在引擎事务内比较调用者的修订与当前修订，冲突则不写正文；界面和 CLI 都走同一路径。现有版本值是单调标识，不能假设每次编辑只加 1。首先验证能否复用它，不为此建立第二个草稿库。
2. **原子受理发送。** 同一事务里校验并冻结草稿修订、记录请求去重标识、关联唯一发送任务。重试返回原操作；换请求标识也不能绕过同一未解决草稿修订的发送锁。存储仍使用原 SQLite，不另造任务调度器。
3. **保留真实发送阶段。** 至少区别尚未开始、已开始但结果未确认、服务端已接受；把已发送副本写入结果单独记录。启动时不能将“已开始”直接转成成功，应保留 `unknown` 并核对，不能自动重投。

这些是下一项实现实验的边界，**本轮未修复上述问题**。需要自己构建的引擎通过同样故障注入后，才能推进真实邮箱的 UI / CLI 共用编辑与发送验收。暂不扩展标签、规则、内置 AI 或完整页面实现。

## 复现

沿用 [本机验证](native-validation.md) 的源码、预编译产物和 Python 环境，在仓库根目录运行：

```sh
sandbox-exec -f research/harness/loopback-only.sb \
  research/.local/venv/bin/python research/harness/check-engine-contracts.py \
  --upstream research/.local/Mailspring \
  --binary research/.local/prebuilt/mailsync \
  --output research/.local
```

脚本校验预编译产物指纹后执行；它是固定版本的行为复现实验，未来修复后应另写产品契约断言，不能继续以“复现缺口”为通过标准。本轮没有验证 Gmail / Graph、邮件送达、真实 OAuth、多账号权限撤销、附件冲突或正式 macOS 沙箱与分发。
